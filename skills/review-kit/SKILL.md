# 代码评审（review 工具）

用 `review` 工具对一次代码改动做只读评审。它不是「再问一遍模型」，而是四道机制叠在一起：

1. **引用可校验**：每条发现必须逐字引用改动快照里的真实代码行；引用不存在的行会被直接拒收（记为「无效引用」，不是误报）。
2. **对抗复核**：每条发现派独立复核者，任务就是推翻它；证据不足按未通过处理。
3. **归属区分**：报告区分「本次改动引入」与「基线中原本存在」。
4. **覆盖透明**：哪些视角跑了、哪些失败、哪些文件没看到、哪些被预算裁掉，全部写出来。

## 什么时候调用

- 刚完成一处功能或修复，想确认没有引入回归；
- 提交、合并、开 PR 前自查；
- 用户说「审一下」「review 一下」「看看这次改动有没有问题」。

**不要**在没有任何代码改动时调用；也**不要**用它讨论设计（直接对话即可）。

## 参数怎么选

| 场景 | 调用 |
|---|---|
| 默认：审工作区未提交的改动 | `review()` |
| 审相对某个分支的改动 | `review({ target: "base", base: "origin/main" })` |
| 审某一次提交 | `review({ target: "commit", commit: "<sha>" })` |
| 审指定文件 | `review({ target: "files", files: ["src/a.ts", "src/b.ts"] })` |
| 小改动想省钱 | `review({ depth: "quick" })` |
| 只看安全 | `review({ lenses: ["security"] })` |

- `depth: "quick"`：最多 2 个视角、最多复核 4 条；`full`（默认）：全部视角、最多 12 条。
- 预计子代理数超过上限时会自动降级为 quick；如果 quick 仍超限，工具会报错并要求收窄范围。

## 结果怎么读

工具返回一段 markdown。按这个顺序读：

1. **确认项**：每条带 `文件:行`、逐字引用的源码行、失败场景、复核结论与置信度、归属。这些是本次最值得处理的。
2. **被推翻项**：折叠在 `<details>` 里，附复核理由。**不要**把它们当成问题汇报给用户；它们是被证伪的假设。
3. **未验证项**：复核者不可用（超时/失败），按配置单列。不要当成已确认。
4. **覆盖**：`✅ 已跑无发现` / `✔ 已跑有候选` / `⚠️ 失败`。**覆盖缺口必须转述给用户**——"没有确认项"只有在覆盖完整时才能说成"没发现问题"。
5. **跳过**：文档文件、二进制、过大文件、超出预算的文件；如实说明。

如果没有确认项，正确说法是：「在已覆盖的 N 个文件、M 个视角里没有可确认的问题，但有 K 个覆盖缺口」，而不是「代码没问题」。

## 纪律

- 评审是只读的：不要因为评审结果就自动修改代码。要修就单独开一轮，改完可以再评审一次。
- 不要反复重跑同一个范围来"碰运气"；一次没确认就按报告转述。
- 报告里的代码引用是评审证据；如果用户要求，可以指出对应文件与行号让用户自己看。
- 工具会派子代理，耗时较长（常见几十秒到几分钟）。调用一次就够，不要并行发多个 review。
